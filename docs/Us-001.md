## User Story

> **Como** jogador autenticado com um deck configurado,  
> **eu quero** que meu ranking e minha pontuação sejam atualizados automaticamente ao final de cada batalha, e que eu receba uma carta de recompensa quando vencer,  
> **para que** minha progressão no jogo seja refletida de forma consistente e recompensadora após cada partida.

---

## Contexto / Motivação

Antes desta história, a batalha não refletia a evolução do jogador: o campo `position` era persistido de forma estática no banco de dados e não havia recompensa tangível para o vencedor. Com esta entrega, o `rank` passa a ser um atributo persistido do usuário enquanto a posição no ranking é calculada dinamicamente pela ordenação de pontos, garantindo consistência. Além disso, a resposta da API passa a retornar os movimentos de cada round, tornando o resultado mais transparente para o cliente.

## Critérios de Aceitação

### AC-01 — Atualização de ranking ao final da batalha

```gherkin
Given  um usuário atacante autenticado com deck configurado
And    um usuário defensor com deck configurado
When   o atacante executa uma batalha pela rota POST /battle
Then   a resposta HTTP deve ser 200
And    o campo "ranking" deve conter o rank e os pontos atualizados do atacante
And    o banco de dados deve refletir o novo valor de "rank" para ambos os usuários
```

---

### AC-02 — Recompensa em carta para o atacante vencedor

```gherkin
Given  uma batalha encerrada onde o atacante é o vencedor
When   a resposta da batalha é retornada ao cliente
Then   o campo "reward_card" deve estar presente na resposta
And    deve conter os dados da carta recebida como recompensa
```

---

### AC-03 — Ausência de recompensa quando o atacante perde

```gherkin
Given  uma batalha encerrada onde o atacante é o perdedor
When   a resposta da batalha é retornada ao cliente
Then   o campo "reward_card" deve ser nulo ou ausente na resposta
```

---

### AC-04 — Retorno dos movimentos por round

```gherkin
Given  uma batalha executada com múltiplos rounds
When   a resposta da batalha é retornada ao cliente
Then   cada objeto de round deve conter os campos "attacker_move" e "defender_move"
And    os movimentos devem corresponder às ações realizadas em cada round
```

---

### AC-05 — Campo "position" substituído por "rank"

```gherkin
Given  qualquer endpoint que retorne dados de usuário ou de ranking
When   o cliente consulta GET /users ou GET /ranking
Then   a resposta não deve conter o campo "position"
And    deve conter o campo "rank" com o valor persistido do usuário
```

---

### AC-06 — Cobertura de testes de integração

```gherkin
Given  a suíte de testes de integração do projeto
When   os testes são executados
Then   "test_battle_routes.py" deve cobrir cenários de batalha (vitória, derrota) e tratamento de erros
And    "test_user_routes.py" deve cobrir cadastro, busca e exclusão de usuários
And    todos os testes devem passar sem falhas
```

## Notas Técnicas

- A **posição** no ranking é calculada dinamicamente pela ordenação de pontos no momento da consulta — não é mais persistida no banco de dados.
- O campo `rank` continua sendo um atributo persistido no modelo `User`.
- A execução das **migrations** é obrigatória antes de testar em ambiente local.
- A recompensa em carta (`reward_card`) só é concedida ao **atacante** vencedor, não ao defensor.
