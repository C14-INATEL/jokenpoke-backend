## User Story

> **Como** usuário já cadastrado na plataforma,  
> **eu quero** autenticar-me através de um endpoint dedicado de login informando meu `username` e `password`,  
> **para que** eu receba um `access_token` JWT válido e possa acessar as rotas protegidas da API, como a de batalha, sem precisar realizar um novo cadastro.

---

## Contexto / Motivação

O `LoginUserUseCase` já existia no projeto e era responsável por validar credenciais e gerar o token JWT, porém essa lógica não estava exposta por nenhuma rota da API. O PR #24 expôs o endpoint `POST /auth/login` com body JSON, completando o fluxo de autenticação básico.

Após a exposição da rota, identificaram-se três problemas complementares tratados no PR #27: o Swagger UI enviava `application/x-www-form-urlencoded` enquanto a rota esperava `application/json`, impedindo o uso do botão **Authorize**; o `passlib[bcrypt]` gerava warnings de depreciação com versões recentes do `bcrypt`; e o `python-multipart` — obrigatório para `OAuth2PasswordRequestForm` funcionar no FastAPI — não estava declarado explicitamente nas dependências.

O PR #28 encerrou a história com testes de integração de ponta a ponta para toda a camada de autenticação, isolados em banco SQLite para não interferir na suíte unitária existente.

## Critérios de Aceitação

### AC-01 — Login com credenciais válidas

```gherkin
Given  um usuário já cadastrado na plataforma
When   o cliente envia POST /auth/login com "username" e "password" corretos
Then   a resposta HTTP deve ser 200
And    o body deve conter os campos "message" e "access_token"
And    o "access_token" deve ser um JWT válido
```

---

### AC-02 — Login com credenciais inválidas

```gherkin
Given  uma requisição POST /auth/login
When   o cliente envia "username" ou "password" incorretos
Then   a resposta HTTP deve ser 401
And    o body deve conter uma mensagem de erro indicando credenciais inválidas
And    nenhum "access_token" deve ser retornado
```

---

### AC-03 — Padronização dos schemas de entrada e saída

```gherkin
Given  o endpoint POST /auth/login está disponível
When   o cliente inspeciona o contrato da rota (ex.: via /docs)
Then   o schema de request deve aceitar "username" e "password"
       via "OAuth2PasswordRequestForm" (form-data)
And    o schema de response deve ser "LoginUserResponse"
       contendo "message" e "access_token"
```

---

### AC-04 — Compatibilidade com Swagger UI OAuth2

```gherkin
Given  o servidor em execução e o Swagger acessível em /docs
When   o desenvolvedor clica em "Authorize", preenche "username" e "password"
       de um usuário cadastrado e confirma
Then   o Swagger deve autenticar com sucesso sem erros de content-type
And    os endpoints protegidos devem poder ser executados diretamente pelo Swagger UI
```

---

### AC-05 — Token JWT utilizável em rotas protegidas

```gherkin
Given  um "access_token" obtido via POST /auth/login
When   o cliente utiliza o token no header "Authorization: Bearer <token>"
       em uma rota protegida, como POST /battle
Then   a rota protegida deve aceitar a requisição sem retornar 401 ou 403
```

---

### AC-06 — Hashing de senha sem warnings de depreciação

```gherkin
Given  o servidor em execução com as dependências instaladas
When   um usuário realiza cadastro ou login
Then   nenhum warning de depreciação relacionado ao "passlib" ou "bcrypt"
       deve ser emitido no console
And    o hashing deve ser realizado via "bcrypt.hashpw" e "bcrypt.checkpw" diretamente
```

---

### AC-07 — Dependências obrigatórias declaradas explicitamente

```gherkin
Given  o arquivo "pyproject.toml" do projeto
When   ele é inspecionado
Then   "python-multipart" deve estar listado como dependência explícita
And    "bcrypt >= 5.0.0" deve estar declarado
And    "passlib" não deve ser mais uma dependência do projeto
```

---

### AC-08 — Cobertura de testes de integração para registro e login

```gherkin
Given  a suíte de testes de integração do projeto
When   os testes são executados com
       "poetry run pytest tests/integration/test_auth_routes.py -v"
Then   exatamente 5 testes devem passar
And    os testes devem cobrir: registro com sucesso, login com sucesso,
       login com senha inválida, login com usuário inexistente
       e retorno do JWT após registro
And    o lint "poetry run ruff check" deve retornar "All checks passed!"
```

---

### AC-09 — Isolamento do ambiente de testes de integração

```gherkin
Given  o conftest de integração em "tests/integration/conftest.py"
When   os testes de integração são executados
Then   eles devem usar um banco SQLite em arquivo isolado via "dependency_overrides"
And    a execução não deve interferir nem quebrar a suíte de testes unitários existente
```

## Notas Técnicas

- O `LoginUserUseCase` já existia antes desta história; o PR #24 apenas expôs a lógica via rota REST com body JSON.
- O PR #27 substituiu o body JSON por `OAuth2PasswordRequestForm` (form-data), alinhando a rota ao `tokenUrl` declarado no `OAuth2PasswordBearer` de `auth_dependencies.py`. Esta mudança **não é breaking change** para clients externos, pois form-data é o padrão OAuth2.
- A substituição de `passlib` por `bcrypt` direto (`bcrypt.hashpw` / `bcrypt.checkpw`) elimina uma camada intermediária e resolve os warnings com `bcrypt >= 5.0.0`.
- O `conftest.py` de integração é **isolado** do `conftest` raiz (que mocka settings para testes unitários), evitando conflitos entre as duas suítes.
- O banco de testes usa **SQLite em arquivo** para garantir isolamento completo sem dependência de infraestrutura externa.
- O `conftest.py` criado é reutilizável para os próximos testes de integração (deck, cards, batalha, etc.).
