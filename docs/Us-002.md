## User Story

> **Como** usuário já cadastrado na plataforma,  
> **eu quero** autenticar-me através de um endpoint dedicado de login informando meu `username` e `password`,  
> **para que** eu receba um `access_token` JWT válido e possa acessar as rotas protegidas da API, como a de batalha, sem precisar realizar um novo cadastro.

---

## Contexto / Motivação

O `LoginUserUseCase` já existia no projeto e era responsável por validar credenciais e gerar o token JWT, porém essa lógica não estava exposta por nenhuma rota da API. Com isso, usuários só conseguiam obter um token durante o cadastro (`POST /auth/register`), o que tornava o fluxo de autenticação incompleto. Esta história expõe o endpoint `POST /auth/login`, padroniza os schemas de entrada e saída e garante cobertura de testes de integração de ponta a ponta para toda a camada de autenticação.

## Critérios de Aceitação

### AC-01 — Login com credenciais válidas

```gherkin
Given  um usuário já cadastrado na plataforma
When   o cliente envia POST /auth/login com "username" e "password" corretos
Then   a resposta HTTP deve ser 200
And    o body deve conter os campos "message" e "access_token"
And    o "access_token" deve ser um JWT válido
```

---

### AC-02 — Login com credenciais inválidas

```gherkin
Given  uma requisição POST /auth/login
When   o cliente envia "username" ou "password" incorretos
Then   a resposta HTTP deve ser 401
And    o body deve conter uma mensagem de erro indicando credenciais inválidas
And    nenhum "access_token" deve ser retornado
```

---

### AC-03 — Padronização dos schemas de entrada e saída

```gherkin
Given  o endpoint POST /auth/login está disponível
When   o cliente inspeciona o contrato da rota (ex.: via /docs)
Then   o schema de request deve ser "LoginUserRequest" contendo "username" e "password"
And    o schema de response deve ser "LoginUserResponse" contendo "message" e "access_token"
```

---

### AC-04 — Token JWT utilizável em rotas protegidas

```gherkin
Given  um "access_token" obtido via POST /auth/login
When   o cliente utiliza o token no header "Authorization: Bearer <token>"
      em uma rota protegida, como POST /battle
Then   a rota protegida deve aceitar a requisição sem retornar 401 ou 403
```

---

### AC-05 — Cobertura de testes de integração para registro e login

```gherkin
Given  a suíte de testes de integração do projeto
When   os testes são executados com "poetry run pytest tests/integration/test_auth_routes.py -v"
Then   exatamente 5 testes devem passar
And    os testes devem cobrir: registro com sucesso, login com sucesso,
       login com senha inválida, login com usuário inexistente
       e retorno do JWT após registro
And    o lint "poetry run ruff check" deve retornar "All checks passed!"
```

---

### AC-06 — Isolamento do ambiente de testes de integração

```gherkin
Given  o conftest de integração em "tests/integration/conftest.py"
When   os testes de integração são executados
Then   eles devem usar um banco SQLite em arquivo isolado via "dependency_overrides"
And    a execução não deve interferir nem quebrar a suíte de testes unitários existente
```

## Notas Técnicas

- O `LoginUserUseCase` já existia antes desta história; o PR #24 apenas expôs a lógica via rota REST.
- O `conftest.py` de integração é **isolado** do `conftest` raiz (que mocka settings para testes unitários), evitando conflitos entre as duas suítes.
- O banco de testes usa **SQLite em arquivo** para garantir isolamento completo sem dependência de infraestrutura externa.
- O `conftest.py` criado é reutilizável para os próximos testes de integração (deck, cards, batalha, etc.).
