## User Story

> **Como** desenvolvedor ou administrador da API,  
> **eu quero** que a remoção de um usuário exclua automaticamente todos os seus dados relacionados — deck e cards —, sem erros de violação de chave estrangeira,  
> **para que** o banco de dados não acumule registros órfãos e o fluxo de delete seja confiável independentemente do estado do usuário.

---

## Contexto / Motivação

A operação `DELETE /users/{user_id}` falhava com erro de constraint de FK sempre que o usuário possuía um deck montado. Embora o cascade estivesse configurado no ORM, ele não estava definido no banco de dados, e o método de delete não carregava as relações antes de remover o registro. O PR #34 corrigiu a camada User → Deck, garantindo o cascade em ORM e banco simultaneamente. Após essa correção, identificou-se que a FK `deck.card_id → cards.id` também não possuía `ondelete=CASCADE`, o que poderia gerar registros órfãos no deck ao deletar cards do usuário. O PR #35 completou a cadeia de cascade (User → Cards → Deck) e expandiu os testes de integração para validar a limpeza completa.

## Critérios de Aceitação

### AC-01 — Deleção de usuário com deck montado retorna sucesso

```gherkin
Given  um usuário registrado via POST /auth/register
And    um deck montado para esse usuário via POST /decks/{user_id}/build
When   o cliente envia DELETE /users/{user_id}
Then   a resposta HTTP deve ser 200
And    o usuário deve ser removido do banco de dados
```

---

### AC-02 — Registros de deck são removidos junto com o usuário

```gherkin
Given  um usuário com deck montado que foi deletado via DELETE /users/{user_id}
When   o cliente consulta GET /users/{user_id}
Then   a resposta HTTP deve ser 404
And    nenhum registro de deck associado ao usuário deve permanecer no banco
```

---

### AC-03 — Registros de cards vinculados ao deck são removidos sem órfãos

```gherkin
Given  um usuário com deck montado contendo cards associadas
When   o usuário é deletado via DELETE /users/{user_id}
Then   todos os registros de deck vinculados às cards do usuário devem ser removidos
And    nenhum registro órfão deve permanecer na tabela de deck após o delete
```

---

### AC-04 — Cascade garantido em duas camadas: ORM e banco de dados

```gherkin
Given  o modelo de dados do projeto
When   o esquema do banco é inspecionado
Then   a FK "deck.user_id → users.id" deve ter "ondelete=CASCADE" definido no banco
And    a FK "deck.card_id → cards.id" deve ter "ondelete=CASCADE" definido no banco
And    o ORM deve estar configurado com cascade correspondente em ambas as relações
```

---

### AC-05 — Deleção de usuário sem deck também funciona corretamente

```gherkin
Given  um usuário registrado sem deck montado
When   o cliente envia DELETE /users/{user_id}

```

## Notas Técnicas

- O cascade foi corrigido em **duas etapas**: PR #34 tratou a relação User → Deck; PR #35 completou com Card → Deck, formando a cadeia completa `User → Cards → Deck`.
- O erro original ocorria porque o cascade estava configurado apenas no ORM, mas não no DDL do banco — ambas as camadas agora estão alinhadas.
- O método de delete foi ajustado para **carregar as relações antes de deletar**, garantindo que o ORM processe a remoção em cascata corretamente.
- Esta correção impacta diretamente os testes de integração da US-002 (PR #28), que cobrem o fluxo de deleção de usuário em `test_user_routes.py`.
